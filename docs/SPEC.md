# 代码安魂曲 / Code Requiem — 实现规格

> 本文档面向零背景的执行者。读完这一份就能开工，不需要再问任何问题。

---

## 1. 一句话

输入任意一个公开 Git 仓库，输出一份针对这个仓库**生命周期状态**的 AI 生成文档：还活着的给出「代码遗嘱」，已死亡的给出「项目悼词」。

---

## 2. 产品逻辑

```
用户输入仓库地址 (GitHub / GitLab / 本地路径)
        ↓
  [分析层] 纯确定性代码，不调用 LLM
  采集 6 类指标 → 计算健康分 0–100 → 判定生命状态
        ↓
  [生成层] 调用 LLM，只负责把结构化指标写成叙事文本
        ↓
  输出：遗嘱 / 悼词 / 两者叠加
```

**关键约束：分析层必须完全确定性。** 同一个仓库、同一时刻，两次运行必须得到同一个分数。LLM 只允许出现在最后一步的措辞生成，**绝不允许参与打分**。

---

## 3. 健康分算法（满分 100）

六个维度，扣分制。

### 3.1 最后提交距今（30 分）

| 距今天数 | 得分 |
|---|---|
| 0 – 7 | 30 |
| 8 – 30 | 25 |
| 31 – 90 | 18 |
| 91 – 180 | 10 |
| 181 – 365 | 5 |
| > 365 | 0 |

以仓库默认分支的**最后一次 commit 的 committer date** 为准。

### 3.2 Bus Factor（25 分）

**定义**：把所有贡献者按提交数降序排列，累加提交数，当累计占比首次 ≥ **60%** 时，已经数到的人头数就是 bus factor。

```python
def bus_factor(commit_counts):  # dict[author_email] -> int
    total = sum(commit_counts.values())
    if total == 0:
        return 0
    running = 0
    for i, n in enumerate(sorted(commit_counts.values(), reverse=True), 1):
        running += n
        if running / total >= 0.60:
            return i
    return len(commit_counts)
```

**为什么是 60% 而不是 80%**：60% 更早告警。一个人占 60% 就已经是单点，不需要等到 80%。

| bus factor | 得分 |
|---|---|
| 1 | 0 |
| 2 | 10 |
| 3 | 17 |
| ≥ 4 | 25 |

按 **commit author email** 去重，不按 name（同一个人可能有多个 name）。

### 3.3 提交活跃度趋势（15 分）

比较**最近 6 个月** 与 **之前 6 个月** 的提交数。

```python
ratio = recent_6m_commits / max(previous_6m_commits, 1)
```

| ratio | 得分 |
|---|---|
| ≥ 1.0（在增长或稳定） | 15 |
| 0.5 – 0.99 | 10 |
| 0.1 – 0.49 | 5 |
| < 0.1 | 0 |

若仓库总时长不足 12 个月，此项按 10 分计（无法判断趋势）。

### 3.4 依赖健康度（15 分）

解析依赖清单，逐个查询包管理器公开 API 获取**最后一次发布时间**：

| 语言 | 文件 | API |
|---|---|---|
| Python | `requirements.txt` / `pyproject.toml` | `https://pypi.org/pypi/{pkg}/json` → `releases` 里取最新版本的上传时间 |
| Node | `package.json` | `https://registry.npmjs.org/{pkg}` → `time.modified` |
| Go | `go.mod` | 跳过（无稳定公开 API） |

取所有依赖中**最老的**那个距今天数（最弱环节）：

| 最老依赖距今 | 得分 |
|---|---|
| < 180 天 | 15 |
| 180 – 364 天 | 10 |
| 365 – 729 天 | 5 |
| ≥ 730 天 或 已从 registry 删除 | 0 |
| 无依赖清单 | 8（中性分） |

**网络失败或超时（5 秒）时按 8 分计**，不得让整个流程挂掉。

### 3.5 Issue 响应（10 分）

仅 GitHub 仓库，用 `GET /repos/{owner}/{repo}/issues?state=all&per_page=100`。

计算**已关闭 issue** 的 `closed_at - created_at` 中位数：

| 中位响应时间 | 得分 |
|---|---|
| < 7 天 | 10 |
| 7 – 29 天 | 6 |
| 30 – 89 天 | 3 |
| ≥ 90 天 | 1 |
| 无 issue 或无法获取 | 1 |

### 3.6 文档完整度（5 分）

| 条件 | 得分 |
|---|---|
| 有 README + 有安装/使用说明 + 有代码示例 | 5 |
| 只有 README（内容 ≥ 500 字符） | 3 |
| README 存在但很短 | 1 |
| 无 README | 0 |

判断“有安装说明”：README 中出现 `install`、`pip install`、`npm install`、`usage` 等关键词之一。

### 3.7 三种模式判定

| 健康分 | 状态 | 输出 |
|---|---|---|
| **≥ 70** | 存活 | **遗嘱模式** |
| **30 – 69** | 承压 | **临终关怀**（遗嘱 + 悼词叠加） |
| **< 30** | 已故 | **悼词模式** |

### 3.8 参考分布（用于自测）

| 仓库类型 | 预期分数 |
|---|---|
| kornia/kornia（活跃大型库） | 75–90 |
| 单人维护的活跃小项目 | 50–65 |
| 两年没提交的毕业设计 | 5–15 |

如果你的实现对这三类打不出上述区间，说明算法写错了。

## 4. 输出结构

### 4.1 遗嘱（必须包含 5 章）

```markdown
# 代码遗嘱 · {repo_name}

## 一、我留下了什么
<!-- 代码规模、模块数、对外 API 数、被谁依赖（能查到就写） -->

## 二、谁在养我
<!-- 主要维护者、每人提交占比、bus factor 及其含义 -->
<!-- bus factor = 1 时必须明确写："这个人离开，项目即终止" -->

## 三、雷区：千万别动
<!-- 从 git log 里找：长期未改的核心文件、带 FIXME/HACK/XXX 的代码位置 -->
<!-- 至少给出 3 个具体文件路径 -->

## 四、我死后，接手的人按这个顺序做
<!-- 3–5 步，每步可执行，不是"请阅读文档"这种废话 -->

## 五、最后的话
<!-- 一段 ≤ 150 字的总结，语气克制，不要煽情 -->
```

### 4.2 悼词（必须包含 5 章）

```markdown
# 悼词 · {repo_name}

        生于 {首个 commit 日期}
        卒于 {最后 commit 日期}
        享年 {时长，精确到年月}

## 一、它的一生
<!-- 关键时间点：起始、活跃期、衰退期、终止 -->

## 二、死因
- **直接原因**：<!-- 如：依赖已下架 / 最后一次提交信息写了什么 -->
- **根本原因**：<!-- 如：bus factor = 1，唯一维护者离开 -->
- **加速因素**：<!-- 如：README 声称生产可用，但无任何测试 -->

## 三、它留下了什么
<!-- 还在被使用的部分、未完成的承诺（TODO/FIXME 数量） -->

## 四、教训
<!-- 2–3 条，具体，不说教 -->

## 五、结语
<!-- 一段 ≤ 100 字 -->
```

### 4.3 临终关怀

先输出完整遗嘱，再输出完整悼词，中间加一行分隔：

```markdown
---

> 以下是它如果继续这样下去，最终会收到的悼词。
```

## 5. 边界情况（必须处理，不能崩）

| 情况 | 处理 |
|---|---|
| 仓库不存在 / 私有 | 返回明确错误：「无法访问该仓库，请确认它是公开的」 |
| 只有 1 个 commit | 正常分析，bus factor 强制为 1，趋势项按 10 分 |
| 空仓库（0 commit） | 返回：「这个项目还没有出生」 |
| 仓库 > 500MB 或 commit > 50000 | 只分析最近 2000 个 commit，并在结果里标注「已采样」 |
| 无 README | 文档分 0，不报错 |
| 依赖 API 超时 | 按 8 分，标注「依赖信息未获取」 |
| 非 GitHub 仓库（GitLab 等） | 能拿到 git log 就分析，issue 项按 1 分 |

**任何情况下都必须有输出，不允许抛出未捕获异常。**

## 6. 技术栈

| 层 | 选型 |
|---|---|
| 语言 | Python 3.10+ |
| Git 解析 | `GitPython`；克隆用 `git clone --depth 200`（浅克隆，快） |
| 界面 | **Streamlit** |
| LLM | Hugging Face Inference API，模型 `Qwen/Qwen2.5-7B-Instruct`（免费额度） |
| 部署 | Hugging Face Spaces（Streamlit SDK） |
| 依赖 | `gitpython`, `streamlit`, `huggingface_hub`, `requests` |

**LLM 调用失败时**：降级为“仅输出结构化指标”，不生成叙事文本，并在页面顶部提示。**不允许因为 LLM 挂了整个应用不可用。**

## 10. 评分优化提示

评判权重：创意 25% / 实现 30% / 实用 25% / 展示 20%。

- **实现分（30%）最重** → 保证 demo 在任何仓库上都不崩，比多做一个功能值
- **创意分（25%）** → 名字「代码安魂曲」和双模式概念本身就是创意
- **实用分（25%）** → 陈述时强调「工程交接」而不是「写悼词」，前者是真痛点
- **展示分（20%）** → 演示视频一定要剪得干净，60 秒讲完整个概念
