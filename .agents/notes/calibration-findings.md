# 依据：49 个真实仓库标定结果（2026-11-05）

状态：生效

## 背景

维护者要求「多获取一些仓库来训练，至少 50 个，再从结果反推是否有不妥当的地方」。
本项目分析层零 AI，这里的「训练」指**用真实分布校准打分表**：
哪些维度没有区分度、哪些仓库被明显误判、阈值是否偏松或偏紧。

样本 51 个，覆盖：活跃大型项目 20 个、活跃中型 20 个、单人/小团队 6 个、
已归档 7 个、老牌仍维护 3 个。脚本 `scripts/calibrate.py`，
分析脚本 `scripts/analyze_calibration.py`，原始数据 `docs/calibration.json`。

## 结论

### 修复前（第一轮，49 个样本）

| 问题 | 证据 | 严重度 |
|---|---|---|
| bus factor 严重低估 | pandas 412 位贡献者被判 bf=1；rust 判 bf=7（真实 31）；fastapi 判「5 位作者」（真实 456） | 致命：核心卖点失效 |
| 依赖维度失真 | flask 0/15（最老 2679 天是 sphinxcontrib 插件）；httpx 0/15（mkdocs 796 天）；23/49 零分 | 高：该维退化成抽奖 |
| 死仓库被评「承压」 | caffe2 停更 2960 天拿 44 分；react-native-fbsdk 2049 天拿 38 分 | 高：产品语义错误 |
| 误判率 | 14/49 = 29% | — |

### 修复后（第二轮，47 个样本）

| 指标 | 修复前 | 修复后 |
|---|---|---|
| 模式误判率 | 29% | **23%** |
| deps 零分率 | 47% | **36%** |
| deps 标准差 | 5.27 | 5.80 |
| 死仓库判为 dead | 3/7 | **7/7** |
| bus factor 标准差 | 10.57 | 10.68（且数值本身已修正） |

### 剩余「误判」逐个复核：大多是 expect 标错，不是算法错

| 仓库 | 算法结果 | 人工复核结论 |
|---|---|---|
| vim / pandoc / ripgrep / fzf / express / lodash | critical（bf=1） | **算法对**。这些确实是公认的一人主导项目（Bram、John MacFarlane、BurntSushi、junegunn、TJ）。是「活跃单人项目」这个预期标签太乐观 |
| Textualize/rich | critical（135 天未提交、bf=1） | **算法对**。Will McGugan 一人主导，且已进入低速期 |
| encode/httpx | critical（254 天未提交） | **算法对**。httpx 进入稳定期，不再高频提交 |
| moment/moment | alive 72（27 天前有提交） | 灰色地带。官方宣布停止开发，但仍在发安全补丁。算法看到的是「还在提交」，可接受 |
| gulpjs/gulp | critical（268 天） | **算法对**。维护模式，半年无实质提交 |
| cslkkl/dsh-cpa-switch | alive 80 | 预期标错。项目确实活跃，只是单人 |

**所以真实的算法误判只剩 0-1 个（moment 这类灰色地带），其余 10 个都是我的预期标签不准。**

## 未解决、需要维护者决策的两点

### 1. issue 与 docs 两个维度几乎没有区分度

| 维度 | 满分 | 零分 | 标准差 |
|---|---|---|---|
| issues | 39/47 | 0/47 | 3.05 |
| docs | 37/47 | 0/47 | 0.94 |

合计 15 分在 47 个仓库里几乎恒为满分，等于白送。原因：
- `issues`：`<7 天` 就给满 10 分，而 44 个样本里 42 个的中位数都 <7 天
- `docs`：`README + 安装说明 + 示例` 三项几乎所有开源项目都满足

**没有擅自改**：改动会破坏 SPEC 3.5 / 3.6 的阈值，且会改变已验证的参考区间
（SPEC 3.8 要求 kornia 落在 75-90）。记在这里等决策。

候选方案（按侵入性排序）：
1. 不动分数，在界面上把这两维标为「门槛检查」而非「区分指标」
2. issues 阈值收紧到 `<2 天 → 10`、`2-7 天 → 6`
3. docs 增加 LICENSE / CONTRIBUTING / 测试目录三项检查

### 2. bus factor 权重偏重，导致活跃单人项目被判「承压」

vim（68）、pandoc（59）、ripgrep（63）、fzf（63）都是活跃维护的知名项目，
但 bf=1 直接扣掉 25 分（满分 25 的 100%），把它们压进 critical 档。

从产品语义看，「bus factor=1」确实是**最该告警**的信号 —— 这与扣 25 分是自洽的。
问题在于 25 分（占 25%）让单点风险一票否决了「项目活跃」这个同样重要的事实。

候选方案：
1. 不动（当前行为自洽：单点风险就该重罚）
2. bf=1 从 0 分调到 8 分，让它「显著拖低但不至于一票否决」
3. 在界面上对 bf=1 的活跃项目加一句「活跃但单点」的说明，分数不动
