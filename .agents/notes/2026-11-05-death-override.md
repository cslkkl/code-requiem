# 决策：加「死亡否决」——停更项目不再被判为承压 (2026-11-05)

状态：生效

## 问题

49 个真实仓库标定后，`facebookarchive/caffe2` 拿到 44 分（承压），
但它最后一次提交在 2960 天前（八年）。一个死了八年的项目被评为「承压」，
说明打分表存在结构性缺陷：

| 维度 | 得分 | 缺陷 |
|---|---|---|
| 还在维护吗 | 0/30 | 唯一带时间信息，已正确判 0 |
| 靠几个人撑着 | 25/25 | 历史上贡献者多 → 满分 |
| 提交趋势 | 0/15 | 已正确判 0 |
| 依赖健康 | 8/15 | 中性分 |
| 提问有人回 | 10/10 | **历史** issue 响应快 → 满分 |
| 有说明书吗 | 1/5 | — |

34 分来自「历史质量」，把总分从 0 拉到 44，越过 30 分的承压线。

## 决策

加一条否决规则（`src/analyzer.py::_build_metrics`）：

- 最后提交 > 730 天 → 总分封顶 `CRITICAL_MIN - 1`（29），强制落进 dead
- 最后提交 > 180 天 → 总分封顶 `ALIVE_MIN - 1`（69），强制落进 critical

否决触发时把原因写进 `metrics.overrides`，界面与解释层都要展示，
不能悄悄改分数。

## 替代方案（强制）

- **改六维权重**：治不了根。问题不在权重，在于五维衡量的是**历史质量**，
  而「项目现在活着吗」只有一维在回答。权重再调也无法表达「历史再好也不算活着」。
- **让 issue 维度只看最近 6 个月**：方向对，但 GitHub 的 issues 接口没有
  「按 closed 时间筛选」的稳定参数，实现成本高且样本会更稀。否决规则一次解决同类问题。
- **只在总分上做线性衰减**：会让 8 年没动的项目仍有 30-40 分，
  仍然可能被判「承压」，没有解决问题。
- **不改，靠解释层说明**：标定显示 13/49 误判里有 2 个是这一类，
  而这一类在产品语义上最刺眼（「它明明死了」）。必须改。

## 影响

- `caffe2` 44 → 29（dead），`react-native-fbsdk` 38 → 29（dead）。
- `gulpjs/gulp`（268 天）从 45 保持 critical，符合「半年没动但不算死」的判断。
- 新增 `tests/test_override.py`（8 个用例）验证封顶值落进正确的档位。
- `metrics.overrides` 是新字段，`docs/CONTRACT.md` 需同步。
